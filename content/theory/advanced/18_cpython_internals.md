# CPython под капотом — от 0 до 100%

Когда ты запускаешь `python script.py`, что **физически** происходит? Как Python превращает текст в выполнение? Что такое «байткод», который все упоминают?

Эта тема — про реализацию интерпретатора. Зная это, ты понимаешь:
- почему Python медленнее C (и насколько);
- почему `.pyc` файлы есть и зачем;
- зачем нужны GIL, free lists, и как работает GC;
- как один и тот же код может вести себя по-разному в CPython, PyPy, MicroPython.

«Python» — это **спецификация языка**. CPython — это **реализация** на C, и она доминирует (95% использования). Когда мы говорим «Python», обычно имеется в виду CPython.

---

## 1. Что такое CPython

Реализаций Python несколько:
- **CPython** — официальная, на C. То, что ты обычно используешь.
- **PyPy** — на RPython, с JIT-компилятором. Быстрее CPython в разы для горячих циклов.
- **Jython** — на Java, исполняется в JVM.
- **IronPython** — на C#/.NET.
- **MicroPython** — для микроконтроллеров.
- **Pyston**, **Cinder**, **Pyjion** — экспериментальные форки CPython с JIT.

CPython доминирует: pip-пакеты, NumPy, asyncio — всё спроектировано под него. Поэтому почти всё что мы обсудим — про CPython.

Исходники: https://github.com/python/cpython. Если интересно — глянь файлы `Objects/listobject.c`, `Python/ceval.c` — там магия.

## 2. Этапы выполнения скрипта

Когда ты запускаешь `python my_script.py`:

1. **Чтение исходника** — текст файла загружается в память.
2. **Лексический анализ (tokenizer)** — текст превращается в токены: `def`, имя, `(`, число, и т.д.
3. **Парсинг (parser)** — токены превращаются в AST (Abstract Syntax Tree).
4. **Компиляция** — AST превращается в **байткод**.
5. **Интерпретация** — виртуальная машина CPython выполняет байткод по инструкциям.

Python — **не интерпретируемый «по строкам»** язык. Он сначала компилируется в байткод, потом исполняется. Поэтому синтаксические ошибки видны до запуска кода.

```python
def f():
    return 5    # ошибка ниже не помешает определить функцию

print("hello")
this is invalid syntax    # SyntaxError всё равно — на этапе парсинга
```

Если есть syntax error — ничего не выполнится.

## 3. Байткод — что это

Байткод — это «язык» виртуальной машины Python. Это **последовательность простых инструкций**, каждая в один байт (плюс аргументы). Вот пример:

```python
def add(a, b):
    return a + b

import dis
dis.dis(add)
```

Вывод:
```
  2           0 LOAD_FAST                0 (a)
              2 LOAD_FAST                1 (b)
              4 BINARY_OP                0 (+)
              8 RETURN_VALUE
```

Что значит:
- `LOAD_FAST 0` — положить переменную #0 (a) на стек.
- `LOAD_FAST 1` — положить переменную #1 (b).
- `BINARY_OP 0 (+)` — взять два верхних элемента стека, сложить, положить результат.
- `RETURN_VALUE` — вернуть верхний элемент стека.

Виртуальная машина Python — **stack-based**: все инструкции работают со стеком. Это контрастирует с регистровыми машинами (как x86-CPU или JVM).

### Просмотр байткода

```python
import dis

def f(x):
    if x > 0:
        return x ** 2
    return 0

dis.dis(f)
```

Тренировка читать байткод полезна для понимания как работают конструкции. Это и есть «низкоуровневый» Python.

## 4. .pyc файлы

Когда ты импортируешь модуль:
```python
import mymodule
```

Python:
1. Находит `mymodule.py`.
2. Проверяет — есть ли `mymodule.cpython-312.pyc` в `__pycache__/`.
3. Если есть и `mtime` совпадает с .py — загружает байткод напрямую.
4. Иначе — компилирует .py → .pyc.

Это **оптимизация** — компиляция один раз, импорты быстрые.

`.pyc` содержит:
- magic number (версия Python);
- timestamp (mtime исходника);
- сам байткод (сериализованный `code object`).

`__pycache__/` создаётся автоматически. На GitHub принято его в `.gitignore`. На проде не критично.

При запуске **скрипта** (не импорте) `.pyc` не создаётся:
```bash
python script.py    # без .pyc
```

Только при импорте. Чтобы вручную скомпилировать:
```bash
python -m compileall mypackage/
```

## 5. Объект код (`code object`)

Каждая функция имеет связанный с ней `code object`:
```python
def f(x):
    return x ** 2

print(f.__code__)
print(f.__code__.co_code)        # сырые байты байткода
print(f.__code__.co_varnames)    # ('x',)
print(f.__code__.co_consts)      # (None, 2)
print(f.__code__.co_names)       # ()
print(f.__code__.co_argcount)    # 1
print(f.__code__.co_filename)    # имя файла
print(f.__code__.co_firstlineno) # номер строки
```

`code object` — immutable, можно сериализовать, можно создавать руками (через `types.CodeType`).

`code object` **тоже объект Python**, его можно передавать как значение, хранить в коллекциях.

## 6. Frame object

Когда функция вызывается, создаётся **frame** (кадр стека):
```python
import inspect

def f():
    frame = inspect.currentframe()
    print(frame.f_locals)        # локальные переменные
    print(frame.f_globals)       # глобальные
    print(frame.f_code)          # объект кода функции
    print(frame.f_back)          # вызывающий frame

f()
```

В frame хранится:
- ссылка на code object;
- стек значений (на котором работает байткод);
- локальные переменные;
- ссылка на предыдущий frame (стек вызовов).

Когда функция возвращается — frame уничтожается. При исключении traceback — это и есть цепочка frame'ов.

## 7. Виртуальная машина

Сердце CPython — функция `_PyEval_EvalFrameDefault` в `Python/ceval.c`. Это огромный switch-by-opcode (или computed goto в современных версиях):

```c
for (;;) {
    opcode = NEXT_INSTR();
    switch (opcode) {
        case LOAD_FAST: ...
        case STORE_FAST: ...
        case BINARY_OP: ...
        ...
    }
}
```

Каждый opcode — это одна функция/блок кода в C. Это и есть «интерпретация байткода». Виртуальная машина читает один opcode, выполняет его, читает следующий.

### Почему медленнее C

Простой `a + b` в Python:
1. Загрузить `a` со стека (LOAD_FAST).
2. Загрузить `b`.
3. BINARY_OP: вызвать `a.__add__(b)`.
4. `__add__` для int: проверить тип, аллоцировать новый int, сложить.
5. Положить результат на стек.
6. RETURN_VALUE.

В C:
1. `add eax, ebx` — одна инструкция CPU.

Поэтому Python в 50-100 раз медленнее C на чистой арифметике. И в 1000 раз медленнее в горячих циклах. Если важна скорость — Numpy/Cython/C extensions.

## 8. PEP 659 — Specializing Adaptive Interpreter (3.11+)

Python 3.11 принёс **специализирующий интерпретатор**: байткод адаптируется под реальные типы.

Например, для `a + b` он смотрит — оба int? Тогда заменяет `BINARY_OP` на оптимизированный `BINARY_OP_ADD_INT`, минуя проверки типа. Это даёт +25% к скорости в среднем.

Это первый шаг к JIT в CPython. В 3.13 уже есть экспериментальный JIT.

## 9. Сборка мусора (GC) — два слоя

### Слой 1: Reference counting

Уже обсуждали в теме памяти. Каждый объект знает сколько ссылок на него. При 0 — освобождается.

```c
Py_INCREF(obj);    // когда добавляется ссылка
Py_DECREF(obj);    // когда удаляется
// если refcnt == 0 — освобождение
```

Это **детерминировано**: память освобождается **сразу же**.

### Слой 2: Generational GC

Refcount не справляется с **циклами**:
```python
a = []
b = []
a.append(b)
b.append(a)
del a
del b    # циклы остаются — refcount-ы не нули
```

Для этого CPython имеет **отдельный** циклический GC. Запускается периодически:
- при достижении пороговых значений аллокаций;
- сразу выявляет циклы среди контейнерных объектов;
- три «поколения» — gen0, gen1, gen2 — молодые объекты проверяются чаще.

```python
import gc
gc.collect()           # принудительно запустить
gc.get_count()         # счётчики поколений
gc.get_threshold()     # пороги
gc.disable()           # отключить (потом не забыть включить!)
```

Можно отключить если уверен, что у тебя нет циклов — будет быстрее. Но обычно пусть работает.

## 10. Свободные списки (free lists)

Для часто используемых типов CPython держит **списки освобождённых объектов**:

```python
import sys
# Для маленьких int (free list integer)
a = 1234567
b = 1234568
del a, b
c = 1234567   # может быть аллоцирован из free list
```

free lists есть для:
- int (отдельный от small int cache);
- list, tuple;
- frame, function, method;
- dict-key объектов.

Это объясняет почему создание/удаление миллионов мелких объектов не так драматично, как могло бы быть.

## 11. Глобальная блокировка интерпретатора (GIL)

Подробно — в следующей теме (19). Кратко:

GIL — мьютекс, защищающий состояние интерпретатора. **Только один поток** может выполнять Python байткод одновременно. Это обеспечивает thread-safety встроенных типов, но **убивает многопоточность для CPU-bound задач**.

Для I/O-bound — ок (GIL отпускается на блокировках). Для параллельных вычислений — `multiprocessing` или Cython с `nogil`.

В Python 3.13 есть экспериментальный «no-GIL» режим (`--without-gil`).

## 12. Импорты — как они работают

```python
import json
```

Что Python делает:
1. Проверяет `sys.modules` — может уже импортирован?
2. Ищет в `sys.path` — список директорий.
3. Находит `json/__init__.py` (или `json.py`, или `json.so` для C-extension).
4. Если нашёл .py — компилирует в байткод.
5. Создаёт **module object**, заполняет его атрибутами (определёнными в файле).
6. Кладёт в `sys.modules` под ключом `"json"`.
7. Привязывает имя `json` в текущем namespace.

```python
import sys
print(sys.path)
print(sys.modules.keys())
```

Импорт **выполняет код модуля** на верхнем уровне. Если в модуле `print("loaded")` — это будет напечатано при импорте.

```python
# my_module.py
print("loaded")
def f(): pass
```

```python
# main.py
import my_module    # 'loaded'
import my_module    # ничего — уже в sys.modules
```

### Циклические импорты

```python
# a.py
from b import x
y = 1

# b.py
from a import y    # ⚠️ ImportError — a ещё не дорегистрирован
x = 1
```

Решение — реструктуризация модулей или импорт внутри функции:
```python
def f():
    from b import x
    ...
```

## 13. Namespace и __builtins__

В Python несколько уровней пространств имён:

1. **Local** — внутри функции.
2. **Enclosing** — в объемлющей функции (для замыканий).
3. **Global** — на уровне модуля.
4. **Built-in** — встроенные `print`, `len`, `int`, ...

```python
import builtins
print(dir(builtins))    # все встроенные
```

Когда ты пишешь `print(...)`, Python ищет `print` по LEGB.

### Скрытие встроенных

```python
def f():
    print = "hi"     # ⚠️ внутри функции print теперь строка
    print("test")    # TypeError: 'str' object is not callable
```

Не используй имена встроенных как локальные.

## 14. `sys` и `inspect` — самоанализ

CPython даёт API для самоанализа:

```python
import sys

print(sys.version)            # версия Python
print(sys.platform)           # 'linux', 'win32', 'darwin'
print(sys.path)               # пути поиска модулей
print(sys.modules)            # импортированные модули
print(sys.maxsize)            # максимальный int (для платформы)
print(sys.getsizeof(obj))     # размер объекта
print(sys.getrefcount(obj))   # счётчик ссылок
print(sys.getrecursionlimit())
sys.setrecursionlimit(5000)
```

```python
import inspect

inspect.getsource(f)           # исходник функции
inspect.signature(f)           # сигнатура
inspect.stack()                # стек вызовов
inspect.getmembers(obj)        # все атрибуты
```

Это «магия», но иногда нужна — для логирования, метапрограммирования, тестирования.

## 15. Разница версий Python

### Python 3.11 — большой скачок производительности

- PEP 659 — Specializing Adaptive Interpreter.
- Меньше memory overhead для frame'ов.
- Faster CPython — ~25% быстрее в среднем.

### Python 3.12

- Per-Interpreter GIL (начало работы над no-GIL).
- f-string формализован как часть грамматики (раньше был особой формой).
- Type parameter syntax (PEP 695): `def f[T](x: T) -> T`.

### Python 3.13

- **Experimental free-threaded mode** (`--without-gil`).
- JIT компилятор (экспериментальный, copy-and-patch).
- Улучшенный REPL.
- Удаление старых deprecated модулей.

### Python 3.14 (в разработке)

- Дальнейшие оптимизации.
- Lazy imports.
- ...

Стандарт сейчас — 3.11+ для нового кода. 3.8 — минимум для зависимостей. 3.7 — устарел.

## 16. C-extensions

Python можно расширять C-кодом. Самые известные пакеты — `numpy`, `pandas`, `scipy` — это смесь Python + C для скорости.

Способы написания extensions:
- **C API** напрямую — старо, сложно, но контроль полный.
- **Cython** — пишешь на «Python с типами», компилируется в C.
- **CFFI** — связь с готовыми C-библиотеками.
- **ctypes** — то же, в стандартной библиотеке.
- **PyO3** — Rust ↔ Python.

Если у тебя горячий цикл и Python тормозит — рассмотри `numba` (JIT) или Cython.

## 17. Почему «Python — медленный»?

Сводка:

1. **Динамическая типизация** — каждая операция требует проверки типов в рантайме.
2. **Все объекты в куче** — int 28 байт, нет stack-allocated значений.
3. **Reference counting** — каждый INCREF/DECREF дорог.
4. **GIL** — не использует многоядерность.
5. **Stack-based VM** — больше операций чем register-based.
6. **Нет JIT** (в стандартном CPython до 3.13) — нет специализации под реальные данные.

Что с этим делать:
- Профилировать (`cProfile`, `py-spy`) — найти узкие места.
- Использовать встроенные функции (на C) — `sum`, `max`, `sorted`, `set`, `dict`.
- Numpy для числовых массивов — векторизация.
- Cython/Numba для горячих циклов.
- multiprocessing для CPU-bound параллелизма.
- asyncio для I/O-bound.
- Rust + PyO3 для серьёзного ускорения с сохранением Python API.

Часто 80/20: 1-2 функции в коде делают 90% работы. Перепиши их — Python станет «быстрым».

## 18. Что нужно запомнить

- CPython — это: tokenizer → parser → AST → compiler → байткод → VM.
- Виртуальная машина — stack-based, выполняет инструкции байткода.
- `dis.dis(func)` — посмотреть байткод.
- `.pyc` файлы — кэшированный скомпилированный байткод модулей.
- `code object` — immutable объект с байткодом и метаданными.
- Frame object — кадр стека вызова.
- GC двухслойный: refcount + cyclic generational.
- Free lists для часто-аллоцируемых типов.
- GIL — главный мьютекс, ограничивает многопоточность.
- Импорты — выполняют код модуля и кэшируются в `sys.modules`.
- Скорость Python ограничена динамикой; для производительности — Numpy/Cython/numba/Rust.

После этого ты понимаешь, **как** работает Python. Дальше — самая обсуждаемая особенность языка: GIL.
